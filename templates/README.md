# Templates

Starter files for setting up any AI coding agent. Use the [adopt prompt](../adopt.md) to have your agent scaffold these automatically, or grab them manually if you prefer.

## Quick adoption

1. Copy `project-file.md` → rename for your tool (see table below)
2. Have your agent derive project identity, constraints, architecture, and "Before You Start" pointers from your codebase — then review and adjust what only you know
3. Copy `gotcha-log.md` → save in your memory/docs directory
4. First session: let the self-learning loop start naturally — log gotchas as you hit them, agent curates at end-of-session

If your tool has auto-memory (currently Claude Code), also grab `memory-index.md`. If your project has deployment or operational complexity, grab `RUNBOOK.md`.

**Tools without auto-memory**: The project file carries more weight — it's your only auto-loaded file. Keep it lean, use it as an index with task-triggered pointers to the runbook, gotcha log, and ADRs. The self-learning loop still works; promotion just targets the project file directly instead of passing through a memory index.

**Multi-tool teams**: Maintain one canonical project file, symlink or copy to tool-specific locations. The content is the same — only the filename differs.

## The files

- **[`project-file.md`](project-file.md)** — Project identity, constraints, architecture, and "Before You Start" table
- **[`memory-index.md`](memory-index.md)** — Topic index + current state. **Not auto-loaded** — it is reached through a task-triggered pointer in the project file, so if that pointer is missing the file is never read. (For Claude Code specifically: the file the tool auto-loads is the *user-level* `~/.claude/projects/<slug>/memory/MEMORY.md`, a different file that happens to share the name.)
- **[`gotcha-log.md`](gotcha-log.md)** — Structured problem/solution journal with promotion tracking
- **[`hypothesis-log.md`](hypothesis-log.md)** — Provisional positions under observation. Each entry pins the falsification criterion (Method) and revisit deadline (Review by) *before* the data lands. Lifecycle: open → resolved (close or promote to ADR). Complements gotcha log (problems already solved) and ADRs (decisions accepted) by giving a home to bets whose evidence is still in the future
- **[`RUNBOOK.md`](RUNBOOK.md)** — Operational principles and how-to
- **[`review-agent.md`](review-agent.md)** — Reusable skeleton for domain review agents (code review, rubric design, assessment audit, etc.) with self-learning capability
- **[`curate.md`](curate.md)** — End-of-session curation skill that automates the self-learning loop (gotcha review, pattern promotion, memory index update). For Claude Code, install **user-globally** at `~/.claude/skills/curate/SKILL.md` — copy this repo's ready-made `.claude/skills/curate/SKILL.md`, which already carries valid frontmatter, rather than converting the template by hand; for other tools, use as an end-of-session prompt
- **[`audit-context.md`](audit-context.md)** — Periodic structural audit of the layered memory system (duplication, wrong-layer placement, bloat, broken references, gitignore correctness). For Claude Code, install **user-globally** at `~/.claude/skills/audit-context/SKILL.md` (copy this repo's `.claude/skills/audit-context/SKILL.md`); for other tools, run as an ad-hoc prompt monthly or after major restructuring
- **[`update-drift.md`](update-drift.md)** — Framework-drift skill: finds every version stamp in the project (tolerating the six stamp shapes in the wild), lists the releases between the pin and the latest, and triages each into **adopt / decline-with-reason / not-applicable / already-in-force**. Verifies claims by execution rather than by reading, checks the gitignored surfaces `git diff` cannot see, and stops before editing normative files. Promotes `adopt.md` §3 from a copy-paste prompt into a skill — §3 is the one of the three that fires repeatedly. **User-global, never project-local.**
- **[`review-changes.md`](review-changes.md)** — Diff-driven pre-commit review that picks review lenses based on what changed. Templates touched → full 3-4 lens battery (guarantee-preservation, adversarial, doc-accuracy, shell-correctness). Docs-only → adversarial + doc-accuracy. CHANGELOG-only → single adversarial pass. A magnitude gate then trims the depth for genuinely small diffs — with carve-outs, since the most dangerous changes (`.gitignore`, renames, mode changes, anything under `scripts/`, and any loosening of a check) are characteristically tiny. For Claude Code, save **project-locally** as `<repo>/.claude/skills/review-changes/SKILL.md` — never user-globally, since its risk tiers and guarantee lens name files in your tree, and a global copy would shadow every repo's own; for other tools, run as a pre-commit prompt. Complements `tests/lint/run.sh` (deterministic) with judgment-based review
- **[`release.md`](release.md)** — Release skill that walks a version cut: classify the semver bump (with an explicit "does an existing consumer need to act?" rule for MAJOR and a refinement-vs-new-artifact rule for PATCH-vs-MINOR), verify preconditions (clean tree, tag free, tests actually run, version references located), write the changelog entry, sync version strings, commit — then **stop before tagging or pushing**. Publishing is the engineer's call; a pushed tag is permanent for anyone pinned to it. Unlike `curate` and `review-changes`, this one ships `disable-model-invocation: true` — user-typed `/release` only, never model-invoked. For Claude Code, save **project-locally** as `<repo>/.claude/skills/release/SKILL.md` — not user-globally, since its preconditions and version-sync step name files in your tree; for other tools, which have no equivalent flag, run it as a deliberate release-time prompt rather than folding it into a broader instruction
- **[`adr.md`](adr.md)** — Architecture Decision Record template with options matrix, consequences, and "Revisit If" triggers. Save each decision as `docs/decisions/ADR-NNN-short-slug.md` and keep an index in `docs/decisions/README.md`
- **[`work-item.md`](work-item.md)** — Lightweight savepoint for multi-session work (features, migrations, refactors, investigations). Five sections: What & Why, Current Status (the savepoint), Decisions, Open Questions, and Outcome. Not a lifecycle state machine — just enough structure to resume after a context reset. Create one when work spans more than two sessions; save as `docs/work-items/[slug].md` and add a one-line pointer where your tool keeps them — the memory index's Current State section with auto-memory, the project file's "Active work" section without. Fill the Outcome section when the work lands or is abandoned
- **[`coordination.md`](coordination.md)** — Layer 5: contributors, shared constraints, work-in-progress, and convention proposals. Save as `COORDINATION.md` at the project root. Not auto-loaded — reach it via a task-triggered pointer in the project file. Add only when a second contributor joins; with a team of one there is no team-truth-versus-personal-preference distinction to draw, and the upkeep is pure overhead
- **[`checklists/`](checklists/)** — Validation checklists for each workflow stage: [architect](checklists/architect-checklist.md), [test](checklists/test-checklist.md), [implement](checklists/implement-checklist.md), [qa](checklists/qa-checklist.md). Lightweight definition-of-done gates (10-15 items each)
- **[`test-verify-memory.md`](test-verify-memory.md)** — Skill that tests the self-verifying memory protocol (curate Step 0.5) against fixture files with known expected outcomes. For Claude Code, save **project-locally** as `<repo>/.claude/skills/test-verify-memory/SKILL.md` — it names fixture files in your tree; for other tools, use as an ad-hoc prompt
- **[`test-fixtures/memory/`](test-fixtures/memory/)** — Eleven fixture files for testing claim-type detection and verification: passing verify, failing verify, erroring verify, manual verify, guarded-but-unreachable verify (the CANNOT VERIFY disposition), unverified state claims (covering "deployed"/"running", "live", and "working in production" triggers), decision, observation, and pattern. Used by `test-verify-memory.md`
- **[`physics-tests/`](physics-tests/)** — Specialized test-scaffolding family for physics simulation code. Targets failure modes ordinary unit tests miss: integrator drift, wrong order of accuracy, conservation violations, force-asymptotic bugs. Includes energy/integrator skeleton, MMS convergence template, intercomparison template (highest leverage — catches shared-misconception bugs), and conservation-log template. See the family's own [`README`](physics-tests/README.md) for the verification-tier hierarchy. **Unproven scaffolding — the one exception in this directory.** Every other template here has been exercised by this repo or a downstream consumer; this family has never been run against a live simulator. Treat its tolerances, convergence thresholds, and intercomparison protocol as a starting point to validate against your own code, not as settled defaults. If you do run it, [say so](https://github.com/ducroq/agent-ready-projects/issues/25) — evidence closes the gap
